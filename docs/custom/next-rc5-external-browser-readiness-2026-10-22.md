# NEXT RC5 — External Edge / Chrome Profile route readiness (2026-10-22)

**Decision: external company browser not yet configured / not authorized as a NEXT connector.** This is a real workspace-enablement blocker, **not** a regression of the RC5 Browser Broker GUI, whose native Host presentation already passed. This investigation was read-only and performed under Stable Mac-Dev. No company browser pages, login cookies, CDP tabs or user profiles were inspected or changed, and no extra browser or debugging port was launched.

## Observed runtime facts

- RC5 installed Next Core `0.9.2-rc.5` and Stable `1.1.0` remained HTTP 200 at ports 8767 and 8765 respectively; `custom/main` was clean at the beginning of the investigation.
- macOS NSWorkspace reported running **Microsoft Edge** bundle `com.microsoft.edgemac`, process PID `86038` and **Google Chrome** `com.google.Chrome`, PID `45017`. `/Applications/Microsoft Edge.app` is installed, version `155.0.4283.62`; Chrome is also installed. This is an observation at the time of the test, not a persistent profile selection.
- `lsof` tied a TCP **loopback listening socket `127.0.0.1:9222` to the Edge main process PID `86038`**. This is important preflight evidence, **not** proof of a valid canonical `ws://.../devtools/browser/<id>` endpoint, matched authentication, profile, requested operation, login state, user consent, or permission to attach a connector. No HTTP request to the port or WebSocket handshake was made.
- macOS returned **`Operation not permitted`** when the current tool account tried to enumerate Edge/Chrome profile directory labels under `~/Library/Application Support/`. The denial was honored: no TCC bypass, elevated process, provider prompt or copied profile data. Process flags alone did not establish the user-designated profile.
- NEXT installed native Broker page independently showed **0 configured connectors**, **0 configured authenticated Edge profiles**, **0 required-external workspace policies**, **0 company required-Edge policies**. Connector health is explicitly `not_observed`; leases, workers and queue were idle. NEXT Browser Broker is operational, but those counts do **not** assert that an existing Edge session may be reused.

## Configuration plumbing gap (next-only)

`internal/config/browser_policy.go` reads the trusted policy/catalog via `AGENTDOCK_BROWSER_CATALOG_JSON` and `AGENTDOCK_BROWSER_WORKSPACE_POLICIES_JSON` **from the Next Core process environment at startup**. `internal/app/runtime_browser_desktop.go` merely reports the already loaded `r.cfg` and does not persist new routes. The installed Browser Broker GUI is currently read-only for these definitions.

The signed Next package's `Contents/Library/LaunchAgents/dev.dropabit.agentdock.next.core.plist` is generated by `packaging/macos/app-identity.sh` with only `AGENTDOCK_DESKTOP_VARIANT=next` under its `EnvironmentVariables`. `packaging/macos/next_shared_bundle.py` intentionally **requires that exact environment** when validating the signed app package. Do not silently add browser environment values to these signed manifests, mutate the installed `.app`, or set session-global `launchctl setenv` variables (which could contaminate Stable). A supported, explicitly Next-scoped source-level route-config admission/persistence path is needed before connecting an approved company profile.

## Security contract reaffirmed

- Company workspace policy class `company` **requires** `required-authenticated-external`, a specific matching connector/profile ID, a canonical absolute existing workspace root, **at least one exact HTTPS allowed origin**, and an authenticated external **Edge** profile with canonical `user_data_dir` and loopback WebSocket endpoint. `internal/browserpolicy/catalog.go` and `policy.go` reject mismatched, non-loopback or non-canonical definitions.
- The connector catalog is configuration **intent**, never evidence of real connector health, Edge login, or consent. Runtime connector peer identity and authorizations must be validated separately and fail closed. An Edge TCP socket listener alone cannot create a verified connector.
- Under the current live RC5 catalog of zero connectors/policies, **company Edge cannot be treated as ready** and must never be silently sent to Managed Headless Chrome. A direct read-only regression run succeeded for `TestACPBridgeCompanyWithoutVerifiedStatusNeverStartsManaged`, `TestPlannerCompanyIntentAndCanonicalScope`, `TestResolveRoute`, `TestPlannerRejectsInvalidPolicyCatalog`, catalog workspace validation, canonical endpoint validation and config validation (all 3 Go package test invocations PASS). These are source/unit policy tests, **not** a real external browser session UAT.

## Smallest safe next product workflow (explicitly blocked on owner selection)

1. **Owner selects the exact Edge identity** they intend NEXT to use: its browser Profile (name/identity, not credentials), approved company worktree roots, and the HTTPS origins it is allowed to access. Obtain explicit consent before attaching to live Edge/CDP. Do not infer the selected profile from currently open tabs or the existence of port 9222. The user must grant any macOS profile read permission through their normal UI if needed; do not circumvent denied access.
2. **Read-only endpoint validation, after approval:** confirm the specific Edge/CDP WebSocket endpoint and peer identity belong to the approved Profile, without relaunching Edge, changing flags, opening sites or reading unrelated tabs. Abandon on any mismatch or unavailable proof.
3. **NEXT-only configuration repair:** implement a minimal owner-approved way for the Next Core to load and validate a *Next-private* catalog/workspace policy, preserving existing `browserpolicy` canonical validation and fail-closed diagnostics. Do not weaken signed bundle environment contract, stable Next isolation or credential boundary. Avoid a new daemon, global `launchctl` env or speculative broad settings framework. Add focused malformed/mismatched policy tests and verify Next-only persistence across restart. There is currently **no installed runtime write surface** for this; source change/another RC deployment will be needed.
4. **Actual Host UAT after 1–3:** route exactly one authorized read-only company operation through the selected Edge and allowed origin, verify correctly owned lease/page/consent/cleanup and no focus theft, then check that missing/unhealthy Edge is rejected **without** managed fallback. Separately cover a specific Chrome Profile only if the user expressly designates and authorizes it.

**Non-goals now:** no change to Stable `8765`, no Edge/Chrome restart, no TCC bypass, no network/CDP probe, no new untrusted config, no Tag/Release/update-feed activation, no P13/P14 UX work. Core Skills/Next RC5 deployment acceptance remains valid; the missing route is an independent owner-consent/configuration gate.
