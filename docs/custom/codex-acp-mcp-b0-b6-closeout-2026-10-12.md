## B4 startup invariant

1. An explicitly selected, opt-in Next-only Codex ACP profile uses a dedicated **direct native Mach-O** CODEX_PATH, rather than npm JS launcher or symlink, so OS PPID lineage is meaningful. The binary is *never* modified. The isolated CODEX_HOME cannot contain a user/global MCP config.
2. A future trusted Core caller must explicitly call private `prepareNextCodexMCPRegistry` **before** creating the first Session, with an authenticated and stable `requestmeta` principal and a complete `nextCodexMCPConfig`. Actual M8 Allow is required before reservation, Adapter startup or listener creation. `BootstrapNextCodexAppServerBirths` starts its owned Adapter, performs one authenticated nonce/MAC extension request and kernel birth observations of native app-server. No Session is fabricated.
3. Core pins that signed/native-scoped generation in `GenerationPin`, opens a private one-server socket, and holds it for the dedicated app-server generation. Wrapper handshake uses only this nonblocking snapshot and kernel rechecks. No adapter RPC from MCP init thread; no potential thread/start→MCP→ACP diagnostic cycle.
4. `nextCodexMCPConfig` is untrusted input, not an approval token. `nextCodexMCPConfigDigest` v2 binds server ID + wrapper absolute path + backend absolute path + backend args. Both executables must be absolute, regular, executable and non-symlink. Private `attachNextCodexInstrumentedMCP` requires a separate actual M8 Allow, the same authenticated principal and unchanged policy revision/configuration as Prepare. It constructs the stdio request with Core's signed birth and private registrar metadata; individual ACP Sessions retain other host-owned HTTP MCPs. A model prompt cannot supply authority.
5. Both private operations reuse `admitHostOperation` and the actual M8 gate/audit/one-shot settlement. Ask, Deny, unavailable/invalid gate, canceled context and missing/unstable/unauthenticated principal fail before startup resources. Admission never runs under `lifecycleMu`; state is rechecked before dispatch. No live Session is invented and `nextM8ContextForLoadedACP` is not used for bootstrap. Env opt-ins only qualify the source seam; they never supply authentication. No trusted frontend bootstrap route exists, so the seam remains Core-private and `Runtime` never invokes it automatically.

## B5 native cleanup decision

A verified `Core → Adapter → native app-server → wrapper → child` process chain is only *app-server-origin evidence*. Native app-server can host multiple threads that share MCP transport; host-managed HTTP MCP may have other clients. B5 therefore **never issues kill/pkill or a direct PID signal**. A `ReleaseSession` only decrements logical Core-owned references and releases its existing provider resource; if underlying release fails it retains the lease. Once all relevant Sessions have actually closed, the already implemented ACP Adapter `recycleAppServerIfIdle` may gracefully release its own dedicated app-server; we do not invent per-task native MCP ownership from this behavior.

Read-only `Reconcile` labels `still_in_use`, `observed_exited_or_replaced` or `unknown_or_deferred`, always sets `unknown_native_borrowers=true` / `cleanup_allowed=false`, and does not conflate process absence with successful intentional cleanup. The registry `AcceptWithCommit` records its final Core generation proof *before* responding `recorded`, preventing a false positive ACK after scope changes.

## Source-only P5/M8 authorization and cross-Core startup fence (this worktree)

- Success criteria: both private Prepare/Attach operations require trusted context identity and actual M8 Allow; a checksum alone cannot authorize either. M8 fingerprints bind the v2 config digest. Raw executable paths/args, including embedded credentials, never enter approval payloads/history; only a SHA-256 digest does. Approval retries remain exact and principal-bound. Prepare and Attach have distinct actions/grants. No production hook, Rust fork, credential access/copy, installed-app operation or real MCP cleanup was added.
- The existing Next root must be owner-owned, non-symlink and exactly `0700`. A fixed `next-codex-native-generation.lock` uses directory-relative `O_NOFOLLOW`, `O_CLOEXEC`, `0600`, same-UID regular single-link file checks and nonblocking exclusive `flock`. It conservatively reserves the entire Next Codex native generation across configurations/server IDs, before native Adapter bootstrap. No directory is created/repaired by acquisition and no lock is truncated, unlinked or replaced. The pinned root/file identities are rechecked before publishing/attaching and during registrar scope validation.
- The descriptor is retained after uncertain bootstrap failure, so retry/config revision cannot start another native generation in that Runtime. `Runtime.Close` first closes/revokes the owned registrar and tears down the existing owned ACP service, then closes the lock descriptors without removing the lock file. Failed ACP Close retains the descriptor until Core exit. No new PID signal/kill authority exists. Concurrent lock losers close only their own descriptors. Local policy revision change, cancellation or shutdown invalidates pending dispatch; a policy change also prevents subsequent registrar authorization.
- Tests use temporary Next roots, synthetic request principals and deliberately unbootstrappable fixture profiles. They do not sign in, start an installed Adapter/native Codex or prove authenticated session UAT. Coverage includes Prepare/Attach anonymous/unstable/unauthenticated/forged markers, invalid state/config, Ask/Deny audit and credential redaction; exact one-shot retry vs different principal/wrapper; two Core instances sharing one lock, uncertain bootstrap/Close/reacquisition; 16 concurrent contenders; root/file symlinks, wrong modes, hardlinks, replacement preservation; policy revision/shutdown after admission while `lifecycleMu` is held; complete config digest inputs.

## 2026-10-12 B6 additional crash/revision fail-closed safeguards

- The dedicated Next-only startup lock now durably records an **unresolved native generation** before bootstrap using write/`fsync` on its initially empty, owner-private 0600 locked inode, followed by directory fsync. Once bootstrap is attempted, **the journal is deliberately never automatically cleared (a strictly M8-authorized, kernel-proven previous-boot recovery routine is now available)** by `Runtime.Close`, even if the owning process terminates: flock releasing is not proof that orphan native app-server, wrapper, or MCP descendants exited. A second Core refuses any nonempty marker, including damaged/truncated data, even after successful lock acquisition. No daemon names, PIDs, secrets or MCP args are persisted. **This is a safety-first source-only stopgap**, *not* a complete recovery UX: any attempted startup requires separately authorized operator proof and a dedicated future reconciliation procedure before production reactivation. Never edit/delete the journal as an automated retry. Failing closed may block an otherwise legitimate startup; this behavior is intentional until safe reconciliation exists.
- `permission.Store.VerifyDiskState` is an additional **read-only drift detector**, called before source-only Next bootstrap, before attach and on Core listener admission. It checks non-symlink 0600 state.json and compares the in-memory canonical JSON to the actual disk state while holding the local mutex. Different Core epochs, lost policy updates, changed history, symlink replacement or corruption cause rejection. This reduces accidental stale-authority dispatch; it is **not** a cross-process admission+policy write transaction and cannot close races against a concurrent writer after verification.
- Negative tests cover two Store instances with different epochs/policies, symlinked state, durable crash marker after descriptor release, and truncated marker refusing restart. Previously optimistic "Close automatically makes the next native generation safe" tests have been changed to truthful fail-closed assertions.
- None of these changes alter the official Codex CLI, reuse authentication, enable Next production, or perform PID termination. **B6 full release remains BLOCKED** on real authenticated Next-only UAT, full policy mutation transaction semantics and operator-authorized orphan lifecycle reconciliation.
